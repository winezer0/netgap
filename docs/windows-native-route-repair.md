# Windows 原生路由与自动断网修复

日期：2026-10-21。

## 问题与证据边界

用户报告：管理员运行，出口检测成功，但路由动作长期显示处理中，随后提示网络或代理发生变化，再次循环。

代码中已确认：

- 旧 Windows 路由后端反复启动 PowerShell，分别枚举、校验和逐条修改路由，放大了操作时长及状态发生变化的窗口。
- 原变化订阅对每个路由/接口通知直接增加版本号，重复通知或仅寿命变化也可能使观测失效。
- 只有已保存断网任务的失败才有退避；快照建立前的校验失败会在下一轮再次尝试。

尚无用户完整错误日志，不能断言每次失败均由上述同一原因触发，也不能将编译通过作为真实断网成功的证据。

## 原生接口选择

使用 Windows 自带的 Management Infrastructure（MI）客户端，通过本机 WMIDCOM 会话访问 NetTCPIP 提供程序。应用不再为完整路由操作创建 PowerShell 进程，不需要安装独立助手或配置 WinRM 监听。仍依赖 Windows 本机 CIM/WMI 服务和 NetTCPIP 提供程序；不是绕过这些系统服务的纯 IP Helper 后端。

选择该接口的原因是 IP Helper 的活动路由表不能单独替代持久路由管理。持久路由也必须保存、删除和恢复。本机会话在进程内复用，避免每条操作重新启动解释器；性能改善程度仍需实测。

当前原生路由保护面向 Windows amd64/arm64。32 位构建在启用保护时明确拒绝。macOS/Linux 路由后端保持各自的原生实现；共同的失败退避适用于三个平台。

参考：

- [GetIpForwardTable2](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/getipforwardtable2)：原生路由表枚举与内存释放要求。
- [MI_Application_NewSession](https://learn.microsoft.com/en-us/windows/win32/api/mi/nf-mi-mi_application_newsession)：空目标和协议选择本机 WMIDCOM。
- [MSFT_NetRoute.Create](https://learn.microsoft.com/en-us/windows/win32/fwp/wmi/nettcpipprov/create-msft-netroute)：路由属性及创建接口。
- [New-NetRoute 的 PolicyStore 说明](https://learn.microsoft.com/en-us/powershell/module/nettcpip/new-netroute)：默认同时创建持久和活动记录，不能向创建操作指定 PersistentStore。新实现继续保存并处理该副作用。
- 原生 ABI 根据本机 Windows SDK 10.0.26100.0 的 `mi.h`、`netioapi.h` 定义。

## 恢复与取消

1. 枚举两类存储并校验网卡绑定。
2. 保存并同步完整快照和有界任务；保存失败不删除。
3. 首次修改前重新核对出口授权与网络/代理状态。
4. 按持久、活动存储的顺序批量枚举，每类存储一次；逐条匹配目标、属性及当前网卡绑定后调用原生删除接口。删除后再次枚举；存在残留即保留任务，不报告成功。
5. 恢复时保留冲突拒绝、剩余寿命计算、持久创建副作用记录及失败记录保留机制。

MI 操作设置超时，并随上下文取消发出取消请求；取消后读取完成结果再关闭操作，避免提前释放仍被系统使用的实例。总断网动作预算仍为 15 秒，单个无外层期限的 MI 操作默认为 10 秒。系统提供程序完成取消可能需要额外时间，因此不承诺操作在严格的墙钟期限内返回；当前没有隔离进程强制终止后端的机制。

现有快照不被主动删除或转换。新 Windows 记录使用数值形式的协议/发布属性和原生网络 GUID；旧 PowerShell 快照可能不兼容。新删除、保存任务续作和恢复会检查现有快照格式，不兼容时在修改路由前拒绝并保留文件，防止混合两种恢复记录。研发阶段不实现旧格式迁移；存在旧备份时应使用产生备份的版本先恢复，再使用新版本。

## 变化判定与重试

- 用 `GetIpForwardTable2` 记录实际路由键与转发属性，忽略持续变化的 Age、ValidLifetime 和 PreferredLifetime。
- 路由通知重新读取具体条目；仅实际新增、删除或转发属性变化增加版本号。接口通知只有网卡快照实际变化才增加版本号。
- 保留变化版本，防止切网后又切回造成旧观测被接受；不是简单删除版本校验。
- 真实的具体路由、默认路由、接口地址、网关、DNS、跃点和代理变化仍会使旧出口观测失效。没有按目标网址裁剪全部路由，因此真正发生的其他路由变更仍可能使观测重做。
- 首次动作失败及续作失败都采用 1、2、4、8、16、30 秒退避，上限 30 秒；实际重试由监测轮询触发，可能晚于该时间。
- 没有有效任务时，退避结束仍需新的成功区域匹配才能重新动作；不会仅因计时器到期直接删除路由。
- GUI 保留失败原因和下次重试时间，避免每次查询都进入处理中。错误日志增加动作耗时、最早重试时间及快照/首次删除前校验阶段。
