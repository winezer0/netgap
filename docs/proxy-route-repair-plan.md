### 本次确认的剩余问题

下列为静态代码路径确认，未通过故障注入复现。发生频率和系统部署差异仍待验证。优先级针对监控有效性与恢复能力，不代表已经发生真实误删。

#### N1 · P1 · 失败的断网续作会长期阻断出口查询（三平台共用；代码已修复，待回归）

- 依据：[CLI 调度](../internal/monitor/monitor.go)、[GUI 调度](../internal/guiapp/monitoring/manager.go)、[续作执行](../internal/iproute/snapshot.go)。存在 pending 时调度直接进入续作或退避返回，不调用出口查询。
- 触发：已经部分删除路由，后续枚举/删除持续报错；或 GUI 加载了 pending 但当前身份没有删除权限。任务保留后每轮优先续作，没有限制连续失败造成的查询停顿。
- 影响：即使尚有路径能访问 IP API，也可能长期没有新出口信息。正常短暂优先续作合理，持续失败造成查询饥饿不合理。
- 修复：分离断网任务与出口检测调度，退避或失败后保留查询机会；续作只执行原授权目标，新检测不应隐式扩大旧任务范围。明确记录最后有效查询时间与等待原因。
- 当前实现：失败/退避后继续查询；本轮已有旧任务时不再次创建或扩大任务；自动动作使用有界 context，锁等待可取消，系统读取已传递 context。原生同步调用仍不能保证硬超时，详细编译记录见 [进展](proxy-route-repair-progress.md)。

#### N2 · P1 · Linux 系统代理选路不完整（B1/B2 已实施；GNOME/KDE PAC 已有 WSL 原生证据）

最新修复：独立 GIO 助手隔离自动模式调用，区分 GNOME/KDE/无桌面；校验实际后端、配置指纹、候选协议和数量、预算及身份。下方保留修复前分析与 B1 阶段记录，当前限制以本批次结果为准。

- 当前实现：[Linux 系统读取](../internal/detector/system_proxy_linux.go) 使用有界配置快照；[GNOME 手动规则](../internal/detector/proxy_gnome.go) 支持 HTTP/HTTPS 查询的协议分流、SOCKS、共享、绕过与 HTTP 认证。已配置手动模式中的 DIRECT 不落入环境代理。读取、解析及暂不支持模式明确报错；端点 host 为空/port 为 0 表示系统显式禁用该端点。
- 剩余触发：启用 PAC 或使用 GNOME 之外的桌面配置来源；这些路径仍不能宣称已覆盖。B1 的 HTTPS/SOCKS、协议分流与 ignore-hosts 已有规则/本地传输测试。
- 影响：可能把系统要求代理的请求直连，或把应绕过的请求发送到 HTTP 代理，进而影响地区判断和断网决定。
- 后续：B2 接入明确的 PAC 解析后端，并区分“没有可读取的桌面配置”和“已识别配置读取/解析失败”。缺少 gsettings 不能证明其他配置来源不存在。详见 [B1 结果及限制](wsl-gnome-test-results.md)。

#### N3 · P1 · Linux 配置读取没有超时和取消（代码已修复，待故障回归；原生同步限制保留）

- 原问题：[runGsettings](../internal/detector/system_proxy_linux.go) 不接收 context，命令不退出可能永久阻塞本轮检测。
- 当前实现：代理读取共用 3 秒预算；gsettings 使用 CommandContext、独立进程组取消、250ms 管道等待上限及 64KiB 输出限制。指纹共用 5 秒预算，Netlink/路由读取继承父取消；CLI Ctrl+C/SIGTERM 与 GUI 生命周期、手动路由操作传递上下文。
- 错误处理：取消/超时保留可识别分类；已识别配置读取失败与不支持模式不回退直连；每轮重新读取，无永久失败缓存。
- 剩余限制：Windows 系统 API、macOS 同步框架读取及部分接口/文件操作不能由 context 中断，只在返回时拒绝过期结果。不能宣称 3/5/15/60 秒均是全部平台操作的硬上限；原生构建与挂起/取消行为仍待验证。

#### N4 · P1 · macOS 订阅失败后没有自动恢复（代码已修复，原生验证待完成）

最新修复：路由订阅改为持久非阻塞 socket，同步排空事件并退避重建；SCDynamicStore 移除 pthread_once，线程退出、启动失败和读取失效可重试，失败/恢复递增版本。下方依据描述修复前行为。

- 依据：[路由订阅](../internal/darwinroute/route_darwin.go) 通过 sync.Once 初始化，读取失败设置 watchFailed 后永久报错；[系统配置订阅](../internal/macnetwork/native_darwin.m) 通过 pthread_once 初始化，失败或线程退出后没有重建。
- 影响：一次初始化或监听故障即可使后续网络指纹持续失败；监控循环可能仍运行，但无法重新获得有效检测结果，通常只能重启进程。
- 修复：实现有界退避的订阅重建，故障和重建时递增状态版本，丢弃在途结果；恢复完整快照后再允许基于结果修改路由。不能静默忽略通知丢失。

#### N5 · P1 · 缺少监控健康状态，长期无有效结果不够明显（代码已修复，待回归）

- 依据：[GUI 状态](../internal/guiapp/state.go)、[状态组装](../internal/guiapp/service.go) 主要表示 running/stopped；代理不可用的重复日志还会被抑制。
- 影响：用户无法直接判断“循环存活”和“近期成功检测”是否同时成立；持续代理错误、订阅故障、续作等待都可能只体现为日志。
- 修复：增加最后尝试/成功时间、连续失败次数、当前失败分类、待恢复/待续作状态，GUI 与 CLI 使用同一健康语义；恢复后清除过期错误。保持告警可见而不逐轮刷屏。
- 当前实现：HealthTracker、独立 GUI 事件和中英文状态栏、CLI 每轮摘要已接入；停止保留观测、重启创建新会话，旧事件不能覆盖新会话；成功查询清除查询错误，路由错误独立保留。

### 待验证风险，不直接判定为已发生的 Bug

- **macOS 原生代码未编译：** 禁用 CGO 的编译不会覆盖 Objective-C、Apple 框架链接或托盘 GUI。优先补原生构建证据。
- **Windows 双存储恢复：** 仍需验证真实 New-NetRoute 副作用、属性冲突、失败后的备份保留；现有代码调整不等于已验证修复。
- **Linux 查询中途 A→B→A：** 当前主要比较前后快照，可能看不到短暂切换；应补路由/链路/地址等变化版本。规则路由对实际路径的影响也需要纳入验证，不能只比较默认路由。
- **网络绑定过于保守：** Linux/macOS 链路重连或重启可能拒绝旧快照，这是保护策略，不能直接改为放宽；需要提供明确的人工/系统恢复方式。
- **权限和目录：** macOS root/普通用户、GUI/CLI 默认目录不同；Linux GUI 安装目录可能不可写。启动时应提前报告当前快照路径、写入能力和路由权限，避免命中后才暴露不可恢复或无权操作。

## 第一阶段：先修复路由保存与恢复基础

涉及：`internal/iproute/snapshot.go`、`snapshot_windows.go`。

1. **拆分路由身份与可变属性（P1）。**
   - 身份包含稳定网卡标识、目标前缀、下一跳及存储类型；接口索引仅用于当前操作时定位。
   - 同一身份只保留一个恢复目标；新捕获的有效状态更新旧属性，历史记录不同时参与恢复。
   - 使用新快照格式；加载时拒绝错误版本及无效任务，不迁移旧 v2 备份。
2. **修复持久路由恢复语义（P1）。**
   - 区分临时与持久路由的创建参数，按真实 cmdlet 约束实现。
   - 将同一路由在 ActiveStore/PersistentStore 中的关联状态作为整体处理，避免创建持久路由附带的活动记录与后续恢复互相冲突。
   - 操作后读取两个存储确认结果；仅移除已确认恢复成功的备份。
3. **收紧到相关网络的校验范围（P1）。**
   - 校验稳定网卡、网络身份、相关地址族及下一跳适用性。
   - IPv6 临时地址等无关变化不阻止 IPv4 恢复；实际切换网络仍拒绝恢复旧路由。
   - 分开定义查询结果有效性、断网续作范围和恢复适用性，避免共用一个过严的指纹。
4. **移除命令行中的大数据载荷（P2）。**
   - 固定 PowerShell 脚本，结构化数据通过标准输入传递；保持超时、取消、错误输出与资源清理。

完成标准：当前格式快照可读取；重复捕获不产生冲突恢复目标；临时与持久状态可分别确认；部分失败不丢备份。

## 第二阶段：修复部分断网后的持续执行

涉及：`internal/iproute`、`internal/monitor/monitor.go`、`internal/guiapp/monitoring/manager.go`。

1. **增加明确的断网任务状态（P1）。**
   - 状态至少区分：监控中、准备完成、断网待重试、断网完成、等待重新检测。
   - 修改路由前持久保存任务范围和恢复信息，记录未完成目标；完整备份与待删除清单分开维护。
   - GUI 与 CLI 使用一致的执行规则。
2. **续作不依赖重新取得公网 IP。**
   - 进入待重试状态后，先处理任务中的剩余路由，再安排出口查询。
   - 已删除路由视为完成；失败采用有上限间隔的退避，显示剩余数量和原因。
   - 不使用删除前的全局路由指纹阻止续作，因为应用自己的删除也会改变该指纹。
3. **限制旧任务的作用范围。**
   - 每次续作校验具体路由和相关网络身份，只处理原任务确认的目标。
   - 网络变化或出现新路由时重新检测，再决定是否建立或扩展任务；不沿用旧 IP 结果删除新网络路由。
   - 停止监控、关闭自动断网、替换监控实例时停止后续重试；保留恢复信息。
   - 重启发现未完成任务时显示可恢复状态；只有保护重新启用且校验通过后才能续作。
4. **成功以实际结果为准。**
   - 完成前再次枚举默认路由，发现新增项时转入重新检测，不误报全部断网成功。
   - 日志和界面区分出口查询失败、部分断网、重试暂停、全部完成。

完成标准：主路由已删且 API 不可达时，仍可处理原任务的剩余目标；停止操作及时生效；旧任务不会删除新网络路由。

## 第三阶段：修复代理路径可用性

涉及：`internal/ipchecker/checker.go`、`proxy_transport.go`、`internal/detector/proxy.go`、`proxy_routes.go`。

1. **拆分 PAC 和候选路径预算（P1）。**
   - 为规则解析、单候选连接和整体查询分别设置有界预算。
   - 单候选连接超时后，在整体预算内尝试下一条系统授权路径；候选数较多时合理分配剩余时间。
   - 保持 PAC 原顺序；仅在规则明确包含 DIRECT 时直连，不为规避错误擅自绕过代理。
   - 明确区分连接阶段失败、请求发送后失败和用户取消，避免扩大回退条件。
2. **环境变量按目标网址解析（P2）。**
   - 先判断绕过规则与目标协议，再验证实际选中的代理。

   - 继续保持系统规则与环境变量的既有优先级，避免隐式改变路径选择。

完成标准：首个代理无响应时，后续合法候选有执行机会；取消及时结束；结果中的路径与实际成功路径一致。
