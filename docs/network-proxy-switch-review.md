## 修复前概况

当前实现可以在下一轮检测中读取新的系统代理配置，但仍存在恢复失败、状态误报和过期查询执行断网操作的风险。上一轮针对代理退出的修改，在 Windows 上不能识别实际的连接拒绝错误，因此此前“已处理”的结论需要更正。

以代理的四种变化乘以网络的四种变化，可以划分为 **16 类基础场景**。代理进程退出、节点变化、协议变化和 TUN 等属于进一步影响处理结果的子场景，实际组合不限于 16 种。

本文按当前 Windows GUI 代码分析；CLI 差异单独说明。实现依据为当前工作区，包含此前尚未提交的修改。

## 修复前检测规则

1. 每轮调用 `DetectProxyWithSource`：优先读取 Windows 当前用户的静态系统代理；没有可用配置时再读取进程环境变量；仍没有则标记为未启用代理。
2. 启用显式代理时，通过该地址查询出口 IP；未启用时使用 Go 默认 HTTP Transport，它仍可能读取环境代理。
3. 单个 API 超时为 5 秒，一轮查询总超时为 10 秒。代理配置只在本轮开始时读取一次；切网、换代理和停止监控不会取消已经发出的查询。
4. 成功得到 IP 后，使用本地库解析位置，只按省份或城市是否包含配置关键词判断是否命中区域。
5. 命中区域时发出警告；若开启“匹配后删除默认路由”，执行删除，成功后停止监控。请求失败本身不会触发删除路由。
6. API 连续失败超过 10 次即从进程内注册表删除；没有定时恢复或重新探测机制。

依据：[代理检测](../internal/detector/proxy.go)、[IP 查询](../internal/ipchecker/checker.go)、[区域判断](../internal/monitor/monitor.go)、[GUI 监控](../internal/guiapp/monitoring/manager.go)。

## 修复前的 16 类基础场景

“启用”指本程序检测到显式代理配置；“关闭”不等于一定没有 TUN、VPN 或环境代理。以下网络变化均指查询 API 所需的链路；“短暂中断”指曾发生请求失败后恢复。

表中的“区域处理”均指：匹配关键词则警告，开启自动断网才删除路由；不匹配则当前日志输出 `Proxy is healthy`。

| 编号 | 代理变化 | 网络变化 | 当前处理 | 错误或限制 |
| --- | --- | --- | --- | --- |
| 1 | 关闭 → 关闭 | 保持可用 | 查询当前出口，执行区域处理 | 没有显式代理也可能显示“代理健康”；环境代理可能仍参与请求 |
| 2 | 关闭 → 关闭 | 切到另一可用网络 | 后续请求获取新网络出口，执行区域处理 | 不感知网卡或网络身份变化；可能使用切换前查询的结果 |
| 3 | 关闭 → 关闭 | 短暂中断后恢复 | 中断时报错并累计 API 失败；恢复后继续查询 | 中断时间足够长可移除查询器，恢复后无法自动找回 |
| 4 | 关闭 → 关闭 | 持续不可用 | 每轮尝试 API，报查询失败 | 最终可能移除全部查询器，只剩空结果错误；不因断网自动停止监控 |
| 5 | 关闭 → 启用 | 保持可用 | 下一轮读取代理并通过它查询 | 已经开始的直连查询可继续返回，并按旧路径的 IP 执行区域处理 |
| 6 | 关闭 → 启用 | 同时切到另一可用网络 | 下一轮使用新代理和当前网络 | 没有等待网络与代理配置稳定；旧结果可能触发对新网络的断网操作 |
| 7 | 关闭 → 启用 | 短暂中断后恢复 | 先失败，后续轮次重新读配置并尝试代理 | API 可能被中断期间的失败移除；代理未就绪也按普通失败处理 |
| 8 | 关闭 → 启用 | 持续不可用 | 根据代理端口和上游链路产生拒绝、超时或其他错误 | 当前 Windows 拒绝分类失效；这些失败均可能损耗 API 可用列表 |
| 9 | 启用 → 关闭 | 保持可用 | 下一轮按无显式代理路径查询并执行区域处理 | 关闭代理后可能命中区域并断网；直连成功可能被记为“代理恢复” |
| 10 | 启用 → 关闭 | 同时切到另一可用网络 | 下一轮使用新网络的无显式代理路径 | 当前轮仍可能使用旧代理；旧出口结果与新网络没有关联校验 |
| 11 | 启用 → 关闭 | 短暂中断后恢复 | 中断期间失败；恢复后继续查询 | 可能误报代理恢复；恢复能力受 API 是否已被移除影响 |
| 12 | 启用 → 关闭 | 持续不可用 | 下一轮走无显式代理路径并持续失败 | 环境代理可能继续生效；失败仍累计到 API，而不是网络状态 |
| 13 | 启用 → 启用 | 保持可用 | 每轮读取配置；换地址下一轮生效，同端口换节点通过出口 IP 反映 | 不记录配置或节点切换事件；无法撤销切换前已发出的查询 |
| 14 | 启用 → 启用 | 切到另一可用网络 | 后续请求使用当前配置和新链路 | 本地代理端口可正常监听但上游断开；端口存在不能证明代理可用 |
| 15 | 启用 → 启用 | 短暂中断后恢复 | 连接失败时尝试后续 API，恢复后重新查询 | 超时、连接重置、代理返回 502 等没有独立恢复状态，可能移除 API |
| 16 | 启用 → 启用 | 持续不可用 | 持续失败，等待后续轮次 | Windows 拒绝连接未进入等待分支；长期故障可能导致恢复后也无 API 可用 |

正常切换能否自动恢复，取决于查询器仍在注册表中、当前代理协议受支持，以及新链路能够访问至少一个已启用 API。不能简单按“网络恢复了”保证监控也恢复。

## 需要另外区分的代理子场景

| 子场景 | 当前处理与风险 |
| --- | --- |
| 退出代理进程，但系统代理仍指向旧端口 | 下一轮继续连接旧端口，不会主动改为直连。Windows 返回 10061，当前特殊错误判断未命中，仍累计 API 失败 |
| 代理退出时同时关闭系统代理 | 下一轮可能改为直连，也可能回落到启动进程继承的环境代理；直连 IP 仍执行区域判断 |
| 代理重启，地址端口不变 | 注册表中仍有可用查询器时，后续轮次可以恢复请求；已被移除的查询器不会因此恢复 |
| 更换代理地址或端口 | 下一轮读取新配置；本轮仍用旧地址。等待状态只保存一个布尔值，不能区分两个代理故障 |
| 同一监听端口更换节点 | 使用当前节点返回的出口 IP；是否告警只取决于区域关键词，不识别具体节点是否符合预期 |
| 切换到 SOCKS 或带认证的代理 | 解析后未保留协议和认证信息，查询统一拼成 HTTP 代理，可能协议不匹配或出现 407 |
| 使用 PAC 或只设置 Windows SOCKS 代理项 | Windows 检测仅读取 `ProxyEnable` 与静态 `ProxyServer`，不解析 PAC；候选项仅包含 http、https、all，可能显示未启用并直接发起请求 |
| TUN 或 VPN 开关与切换 | 没有专门识别机制；由操作系统路由决定实际路径，然后判断出口区域。“未启用显式代理”可能仍然经过隧道 |

另外，HTTP 与 HTTPS 配置不同代理时，目前只选一个地址用于所有 API。IPv6 代理地址使用字符串拼接，缺少 `net.JoinHostPort`，可能生成不正确的 URL。

依据：[配置解析](../internal/detector/system_proxy.go)、[Windows 配置读取](../internal/detector/system_proxy_windows.go)、[Transport 创建](../internal/ipchecker/checker.go)。

## 修复前代码中的切换风险（状态见顶部）

- **旧结果可能操作新网络。** 查询开始时记录代理配置，但结果返回前没有重新确认网络或代理是否已变；一次切换前的区域匹配结果可能触发切换后网络的默认路由删除。一次有效匹配即可执行，没有稳定期或连续确认。
- **快速停止并重新启动有任务交叉风险。** Stop 立即设置 `running=false`，旧查询还可能运行；此时 Start 可以创建新任务。旧任务的 `finishRun` 会清空共享的 running 和 cancel，旧任务的 `requestStop` 也可能取消新任务。该项由调用顺序确认，未进行真实并发网络切换。
- **“未启用代理”与请求实际路径可能不一致。** 无显式 Transport 时 Go 默认 Transport 仍按请求协议读取环境代理，且其环境配置按进程缓存。程序自有检测优先取 HTTP_PROXY，再取 HTTPS_PROXY、ALL_PROXY；它与 Go 的按协议及 NO_PROXY 规则不一致。只配置 ALL_PROXY 或环境值不被自有解析器接受时，检测与实际请求可能走不同路径。
- **区域判断不等价于代理连通性。** 代理正常但出口命中配置区域，也会警告并可能删除路由；未启用代理但出口不匹配，也会记录代理健康。TUN 或 VPN 不会被单独证明有效，主要看到的是查询 API 这一次请求的出口位置。
- **恢复路由可能使用旧网络的网关。** 恢复操作只读取缓存网关并执行 route add，不确认当前网卡和网关是否仍适用；保存的接口信息未用于恢复。多默认路由场景下，保存与删除也没有精确绑定同一路由。依据：`internal/guiapp/actions.go:69`、`internal/iproute/route.go`。
- **显式代理连接缺少统一复用和回收。** 每次查询新建 Transport，没有主动关闭空闲连接；高频监控时可能累积等待回收的连接，不利于切换期间的连接管理。
- **代理关闭与真正无网络目前没有独立状态。** GUI 主要保留监控运行状态、日志和区域告警，没有明确展示“直连可用、代理不可达、网络不可达、查询服务失败”的区别。

## 修复前 CLI 与 GUI 的差异

两者共用 IP 查询逻辑，因此 Windows 错误码和 API 移除问题都会受影响。CLI 的 `CheckProxyStatus` 与 `StartMonitoring` 都会记录查询错误，尚未应用 GUI 的代理不可用日志去重。

CLI 在命中区域且开启 Shutdown 时，即使删除路由失败，外层仍会按该配置结束监控并记录网络已中断；GUI 则在删除成功后才停止，但删除失败不会重试。两种行为都需要修正。

依据：[CLI 监控](../internal/monitor/monitor.go)、[GUI 监控](../internal/guiapp/monitoring/manager.go)。

## 当时的修正顺序和产品行为讨论

优先修正 Windows 错误分类和网络错误惩罚 API 的机制，再将停止信号传入查询并隔离每次监控任务，保证停止后不能执行路由操作。随后修正删除失败重试和恢复日志，并在执行删除前确认结果仍属于当前网络与代理配置。

实现之前需要明确三个相互独立的行为选择：

| 决策 | 合理选项 |
| --- | --- |
| 用户主动关闭显式代理后 | 继续按出口区域监控；暂停等待代理重新启用；按代理退出事件触发保护 |
| 切换期间无法查询出口时 | 保留监控并等待恢复；超过指定持续时间后触发保护 |
| 自动断网的匹配依据 | 沿用当前区域关键词；改为明确的期望出口范围；区域与代理状态组合判断 |

当前代码实际采用“关闭后继续查询出口、请求失败继续等待、单次区域匹配可触发断网”。这些规则是否符合期望，需要与用户的使用场景对应，不能仅凭代理开关状态推断。
